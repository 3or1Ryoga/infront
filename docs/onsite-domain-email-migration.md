## 2. 絶対に守ること

- ドメイン、Microsoft 365、Vercelの所有者と復旧先は会社にする。
- パスワード、決済情報、回復コード、セッショントークンをこのリポジトリへ保存しない。
- DNS変更前に、既存レコード全件・ネームサーバー・TTLを記録する。
- 必要なメールボックスを全部作る前にMXを変更しない。
- eoメールは、新メールの稼働確認直後に解約しない。
- SPFは同一ドメインに複数作らず、1レコードへ統合する。
- 不明なDNSレコードを推測で削除しない。

## 6. 実施手順

### A. ドメイン取得

1. レジストラで候補の空きを再確認する。
2. 会社担当者が候補と費用を承認する。
3. 会社名義、会社住所、会社の支払方法で取得する。
4. 自動更新、二要素認証、移管ロックを有効にする。
5. 復旧コードを会社の安全な保管場所へ保存する。
6. 管理責任者と更新責任者を記録する。

ドメインをVercelで買う必要はない。別のレジストラで所有し、DNSからVercelとMicrosoft 365へ接続できる。

### B. Microsoft 365準備

1. 既存の法人テナントがあるか確認する。ある場合は新規作成しない。
2. 必要数と既存Outlookライセンスを基にプランを決める。
3. 全利用者を作成し、多要素認証を設定する。
4. Microsoft 365管理センターで独自ドメインを追加する。
5. まずTXTレコードだけで所有権を確認する。
6. 希望メールアドレス、エイリアス、共有メールボックスをすべて作成する。
7. MX変更前の状態を記録する。

### C. WebをVercelへ接続

1. 本リポジトリを公開している正しいVercelプロジェクトか確認する。
2. Vercelへ `infront-kohsan.co.jp` と `www.infront-kohsan.co.jp` を追加する。
3. Vercelが提示するAまたはCNAMEレコードをDNSへ追加する。
4. apexと`www`のどちらを正規URLにするか決め、もう一方をリダイレクトする。
5. HTTPS証明書が有効になるまで確認する。

Web用レコードを設定しても、Microsoft 365用のMX/TXT/CNAMEを削除しない。

### D. メール切り替え

実施条件:

- [ ] メールアドレス一覧が承認済み
- [ ] 必要なユーザーとメールボックスが作成済み
- [ ] 管理者が2名以上、または会社が復旧手段を保有
- [ ] 旧メールの保存・移行方針が確定
- [ ] 現在のDNSを保存済み
- [ ] ロールバック担当者が決まっている

条件を満たしたら、Microsoft 365管理センターがそのドメイン専用に提示する値を使用して以下を設定する。

- MX: Exchange Onlineへ配送
- TXT: SPF
- CNAME: Autodiscover
- CNAME: DKIM用セレクター（管理センターの値を使用）
- TXT: DMARC

値を記憶や一般例から決めず、対象テナントの管理画面に表示された値を転記する。

DMARCは最初から強制拒否せず、既存の送信元を確認しながら段階的に強化する。複合機や外部サービスが会社ドメインで送信する場合は、SPF/DKIM設計へ含める。

### E. Outlookと旧メール

1. 新しいMicrosoft 365アカウントをOutlookへ追加する。
2. 過去メールを移す場合は、元データのバックアップを先に取る。
3. POP利用時は、端末内のデータファイルを確認してから移行する。
4. 署名、連絡先、予定表、ルールを必要に応じて移す。
5. eoで転送が可能なら新アドレスへ設定する。
6. 旧アドレスの自動返信または署名で新アドレスを案内する。
7. eo契約は合意した移行期間が終わるまで維持する。

eo側が所有するドメインの旧アドレスは、独自ドメインへ「移管」できない。旧アドレスを残す、転送する、周知する、の組み合わせで移行する。

## 8. 障害時の停止・復旧

新メールが受信できない場合:

1. 追加変更を止める。
2. Microsoft 365のサービス状態、ドメイン状態、ユーザー、ライセンスを確認する。
3. DNSのMX、TXT、CNAMEと伝播状況を確認する。
4. 切り替え直前の記録と比較する。
5. 短時間で解消できず業務影響がある場合、保存した旧MXへ戻す。
6. eoで受信できることを確認する。
7. 原因と変更内容を時刻付きで記録する。

DNSの反映には時間差があるため、変更を連続して重ねない。復旧時も保存した正確な値を使い、推測で入力しない。
